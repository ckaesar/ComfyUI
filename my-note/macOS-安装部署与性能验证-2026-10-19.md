## 6. 模型选择：16 GB 内存的关键取舍

### 6.1 为什么放弃 bf16

| 组合 | 文件 | 体积 |
|------|------|------|
| BF16 | `z_image_turbo_bf16.safetensors` | 约 12.3 GB |
| | `qwen_3_4b.safetensors` | 约 8.0 GB |
| | `ae.safetensors` | 0.32 GB |
| | **合计** | **约 20.6 GB** |

本机 16 GB 统一内存，`torch.mps.recommended_max_memory()` 只有 **11.8 GB**。即使文本编码器与扩散模型先后加载，峰值仍会超过物理内存，只能走 swap，导致极慢甚至 OOM。

### 6.2 最终采用的 INT8 组合

| 角色 | 文件 | 字节数 | 目录 |
|------|------|--------|------|
| 扩散模型 | `z_image_turbo_int8_convrot.safetensors` | 6,201,001,296（5.8 GiB） | `models/diffusion_models/` |
| 文本编码器 | `qwen_3_4b_fp8_mixed.safetensors` | 5,631,994,051（5.2 GiB） | `models/text_encoders/` |
| VAE | `ae.safetensors` | 335,304,388（320 MiB） | `models/vae/` |
| | **合计** | **约 11.0 GiB** | |

对应 ComfyUI 内置工作流模板：`image_z_image_turbo_int8.json`。

### 6.3 下载方式与踩坑

下载源实测（不同时段差异较大，仅作参考）：

| 源 | 扩散模型 | 文本编码器 |
|----|----------|------------|
| HuggingFace 直连 | 约 0.75–2.2 MB/s | 约 0.75 MB/s |
| hf-mirror.com | 约 60 KB/s（较慢） | 约 1.0 MB/s |
| ModelScope | 测速约 0.79 MB/s | 测速约 56 KB/s（受并发影响） |

最终做法：**两个文件并行、分别走不同源**，总带宽约 1.8–2.5 MB/s。

踩坑 1：连接被对端重置

```text
curl: (56) Recv failure: Connection reset by peer
```

`--retry` 默认不重试这类错误，进程会直接退出。改为「外层循环 + `--retry-all-errors`」，断了就续传，直到文件达到预期大小：

```bash
F=models/diffusion_models/z_image_turbo_int8_convrot.safetensors
U=https://huggingface.co/Comfy-Org/z_image_turbo/resolve/main/split_files/diffusion_models/z_image_turbo_int8_convrot.safetensors
S=6201001296
while [ "$(stat -f%z "$F" 2>/dev/null || echo 0)" -lt "$S" ]; do
  curl -L -C - --retry 20 --retry-delay 5 --retry-all-errors \
       --speed-limit 10240 --speed-time 60 -o "$F" "$U"
  sleep 5
done
```

踩坑 2：下载中的文件被 ComfyUI 误加载

下载未完成时先把文件命名为 `.part`，完成后校验通过再改回 `.safetensors`。

### 6.4 完整性校验（离线）

safetensors 自带长度信息，无需联网比对哈希：

```python
import json, os, struct

for p, expected in [
    ("models/diffusion_models/z_image_turbo_int8_convrot.safetensors", 6201001296),
    ("models/text_encoders/qwen_3_4b_fp8_mixed.safetensors", 5631994051),
    ("models/vae/ae.safetensors", 335304388),
]:
    size = os.path.getsize(p)
    with open(p, "rb") as f:
        n = struct.unpack("<Q", f.read(8))[0]
        header = json.loads(f.read(n))
    header.pop("__metadata__", None)
    end = max(v["data_offsets"][1] for v in header.values())
    print(p, "complete:", size == 8 + n + end == expected)
```

三个文件均校验通过。

## 7. 下载期间防止睡眠

macOS 睡眠会挂起进程和网络，导致下载中断。本机 AC 电源下 `sleep 1`（空闲 1 分钟即睡眠），必须处理。

```bash
caffeinate -i -m -s -w <监控进程 PID>
```

- `-i` 阻止空闲睡眠，`-m` 阻止磁盘睡眠，`-s` 阻止系统睡眠（AC 下有效）
- `-w PID` 绑定进程：监控进程结束（下载完成）时自动退出，无需手工清理
- 用 `pmset -g assertions` 可确认断言已生效

限制：**合上盖子仍会睡眠**，下载期间需保持开盖。

## 8. 首次出图失败与修复

第一次运行采样正常完成，但在 `SaveImage` 失败：

```text
[INFO] Requested to load PixelspaceConversionVAE
[INFO] loaded completely;  0.00 MB loaded, full load: True
[ERROR] !!! Exception during processing !!! Cannot handle this data type: (1, 1, 16), |u1
```

原因：工作流里 `VAELoader` 选的是内置的 `pixel_space` 假 VAE。它的 `decode` 原样返回输入，Z-Image 的 16 通道 latent 直接交给 `PIL.Image.fromarray` 就会报错。

修复：把 `VAELoader` 改为 `ae.safetensors` 后重新运行，正常出图。

> 该问题与此前 Windows 机器上的记录（2026-09-30 · VAELoader 误用 pixel_space）完全相同。

## 10. 性能数据

### 10.1 多次运行实测

| # | 场景 | 总耗时 | 采样 | 每步 | 模型加载 |
|---|------|--------|------|------|----------|
| 1 | 服务启动后首次 | 62.96 s | 35.0 s | 4.40 s/it | 是 |
| 2 | 重启后首次 | 61.62 s | 35.0 s | 4.46 s/it | 是 |
| 3 | 输入完全相同的重跑 | 0.00 s | — | — | 否（全图缓存命中） |
| 4 | 修改 seed 后重跑 | 60.19 s | 33.0 s | 4.25 s/it | 是 |

冷启动耗时拆分：

| 阶段 | 耗时 | 占比 |
|------|------|------|
| 8 步采样 | 33–35 s | 约 55% |
| 模型加载 + 文本编码 + VAE 解码 | 约 27 s | 约 45% |

加载量：文本编码器 5371.00 MB + 扩散模型 5889.08 MB + VAE 159.87 MB。

### 10.2 与旧 Windows CPU 机器对比

| 指标 | Windows（CPU） | macOS M5（MPS + INT8） |
|------|----------------|------------------------|
| 512×512，8 步 | 约 40 分钟 | **约 60 秒** |
| 加速比 | — | **约 40 倍** |

### 10.3 为什么模型缓存保不住

16 GB 内存装不下 11.2 GB 模型，ComfyUI 启用的是内存压力缓存：

- 每执行完一个节点都会检查可用内存，不足就淘汰缓存（[execution.py](../execution.py#L801-L813)）
- 淘汰时**旧的 ModelPatcher（已加载模型）优先被清掉**（[comfy_execution/caching.py](../comfy_execution/caching.py#L588-L590)）
- 实测第 4 次运行只命中了 `VAELoader`（VAE 仅 160 MB），5.37 GB 和 5.89 GB 两个大模型已被淘汰，必须重读磁盘

因此：**只有输入完全不变时才是 0 秒；只要真正重新生成，就要再付约 27 秒加载成本**。这与是否修改 seed 无关。

## 11. 同时跑 10 张的评估

### 方式 A：`batch_size = 10`（真正并行）

- 权重固定 11.2 GB，激活值随 batch 增长（估算额外 2–6 GB）
- 峰值估算 14–19 GB，超过 16 GB，会触发 swap
- 采样单步可能变为 batch 1 的 3–8 倍，乐观估计总耗时 3–5 分钟，但 swap 后可能严重恶化甚至失败

### 方式 B：队列串行跑 10 个任务（推荐）

- 内存峰值与单张相同，不会翻倍
- 模型能常驻时约 377 秒（27 s + 10 × 35 s）
- 每张都被淘汰重载时约 600 秒（10 × 60 s，本机更可能是这种情况）

结论：16 GB 机器建议 **batch_size=1 + 队列串行**；想提高吞吐可先实测 batch 2–4。

## 12. 视频生成验证（LTX-Video 2B）

### 12.1 为什么不用 MiniMax H3

本地创建的 `video_minimax_h3_i2v` 任务需要约 39 GB 模型，其中文本编码器 14.61 GB、扩散模型 19.53 GB，远超 16 GB 物理内存，无法运行。

### 12.2 采用的轻量方案

| 角色 | 文件 | 精确大小 | 目录 |
|------|------|----------|------|
| 视频模型（含 VAE） | `ltxv-2b-0.9.8-distilled-fp8.safetensors` | 4,461,695,684（4.16 GiB） | `models/checkpoints/` |
| 文本编码器 | `t5xxl_fp8_e4m3fn.safetensors` | 4,893,934,904（4.56 GiB） | `models/text_encoders/` |
| | **合计** | **8.72 GiB** | |

- 单文件 checkpoint 内含 VAE（读取 safetensors 头部确认含 `vae.*` 键）
- 下载期间 hf-mirror 触发 HTTP 429 限流，改为视频模型走 HF 直连、T5 走 ModelScope，并行约 1.1–1.2 MB/s，约 65 分钟完成
- 两个文件均通过字节数与 safetensors 头校验

### 12.3 测试参数

| 项目 | 取值 |
|------|------|
| 分辨率 | 512 × 512 |
| 帧数 | 49（25 fps，约 2 秒） |
| 采样 | 8 步，`euler`，cfg 1.0 |
| 调度 | LTXVScheduler（max_shift 2.05、base_shift 0.95、terminal 0.1） |
| 输入图 | `input/test_i2v.png`（由 512×512 图片复制） |
| 输出 | `output/video/ComfyUI_i2v_test_00001_.webp`（888 KB） |

### 12.4 耗时

| 阶段 | 耗时 | 占比 |
|------|------|------|
| 8 步采样 | **8.0 s（1.02 s/步）** | 5.5% |
| 模型加载 + 换入换出 + 文本编码 + VAE 解码 | 约 136 s | 94.5% |
| 合计 | **144.05 s** | 100% |

加载明细：

| 模型 | 加载量 |
|------|--------|
| LTXV 扩散模型 | 3667.90 MB |
| T5 文本编码器 | 4541.69 MB |
| VideoVAE | 2378.23 MB |

日志多次出现 `Unloaded partially`（3064 MB、634 MB、3667 MB 被释放后重新加载），说明 16 GB 下 ComfyUI 不断换入换出，这是耗时主因。

### 12.5 内存

| 指标 | 峰值 |
|------|------|
| 最小空闲物理内存 | 0.02 GiB |
| 最大 swap 使用 | 27.13 GiB |
| 内存压缩峰值 | 约 7.3 GiB |

执行过程采样：

| 时刻 | 空闲 | 压缩内存 | swap 已用 |
|------|------|----------|-----------|
| 30 s | 0.06 G | 7.30 G | 25.83 G |
| 61 s | 0.03 G | 6.63 G | 25.69 G |
| 91 s | 0.06 G | 5.34 G | 20.85 G |
| 完成 | 4.82 G | 1.86 G | 15.93 G |

### 12.6 结论

- **能跑**：512×512、49 帧、8 步，约 2 分半产出一条 2 秒视频
- **采样不是瓶颈**（1.02 s/步），94% 时间花在模型换入换出与 VAE 解码
- 提速方向：保持低分辨率与短帧数、关闭其他占内存程序、必要时用 `--lowvram` 启动

## 13. 后续建议

1. **降低固定开销**：换更小的文本编码器（如 Qwen3-4B 的 Q4/Q8 GGUF，约 2.3–4 GB），让模型总占用降到 16 GB 能常驻的水平。
2. **不要用 batch 10**：16 GB 下风险高，优先队列串行。
3. **下载大模型**：用断点续传 + 自动重连循环，下载期间用 `caffeinate` 防止睡眠并保持开盖。
4. **完整性校验**：用 safetensors 头部自校验，不必联网比对哈希。
5. **排查失败**：`/history` 接口能拿到完整异常栈，比终端日志更直接。
